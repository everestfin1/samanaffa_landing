  1. T0 — Simulateur. L’utilisateur choisit un objectif d’épargne (maison, études, etc.), un montant mensuel et une durée. Résultat affiché pour motiver la suite.
  2. T1 — Téléphone & vérification. Saisie du numéro (format international), envoi d’un code OTP par SMS, validation. Création du compte utilisateur et connexion automatique via jeton serveur sécurisé (pas de mot de passe).
  3. T2 — Prénom. Collecte du prénom pour personnaliser l’expérience.
  4. T3 — Questionnaire (3 questions). Situation, capacité d’épargne, expérience → recommandation de formule (ex. Formule Libre).
  5. T4 — Intention de dépôt. Montant du premier dépôt et choix du portefeuille mobile (InTouch). Une intention de transaction est enregistrée ; le paiement réel intervient après validation KYC.
  6. T5 — Vérification d’identité (Didit). Parcours Didit : document d’identité et selfie. Sur ordinateur : modale SDK ; sur mobile : redirection. Statuts : en cours, approuvé, refusé (avec nouvelle tentative possible).
  7. T6 — Écran de succès. Félicitations, rappel du dépôt et de la formule. Bouton vers le portail client (/portal/dashboard).
Après T1 : si la connexion automatique échoue, redirection vers /login?callbackUrl=/onboarding pour reprendre avec le même numéro.

Parcours 2 — Connexion (client existant)

Réservé aux numéros déjà enregistrés lors de l’onboarding. Aucun mot de passe.

Étape A — Saisie du numéro

Validation du format (ex. +221 77 …). Bouton « Recevoir mon code ».

Étape B — Envoi OTP

SMS avec code à 6 chiffres (valide 5 min). Message générique si le compte existe.

Étape C — Saisie du code

Vérification du code. Aide affichée si aucun SMS (« même numéro qu’à l’inscription », lien création de compte).

Étape D — Portail

Redirection vers le tableau de bord ou l’URL demandée (callbackUrl).

Environnement de test : avec MOCK_OTP=true, aucun SMS réel ; le code de test s’affiche en local pour les numéros enregistrés. Numéro inconnu : message explicite en dev uniquement.

Après inscription — Portail client

Une fois connecté, l’utilisateur accède à l’espace sécurisé /portal.

  1. Tableau de bord. Vue d’ensemble des comptes (Sama Naffa, produits liés selon configuration).
  2. Complétion du profil (si nécessaire). Modal : email, acceptation des conditions, signature — avant certaines actions.
  3. Sama Naffa — dépôt. Après KYC approuvé : confirmation du dépôt initié en T4 via InTouch (lien de paiement / instructions).
  4. Profil & KYC. Consultation du statut ; relance Didit depuis le profil si besoin.
  5. Notifications. Mises à jour KYC, transactions, etc.
  6. Déconnexion / session. JWT avec expiration ; déconnexion après inactivité (~15 min) dans le portail.
Liens : ancienne route /register redirige vers /onboarding. Les parcours marketing APE/PEE publics alimentent les sections admin correspondantes.

Parcours 3 — Administration (connexion)

Réservé aux comptes staff. Authentification par email + mot de passe (distinct du parcours client OTP).

Étape A — Page de connexion

/admin/login — saisie email et mot de passe. Branding Sama Naffa / Everest Finance SGI.

Étape B — Vérification serveur

API POST /api/admin/auth/login : contrôle identifiants, compte actif, émission JWT.

Étape C — Session locale

Stockage admin_token, admin_refresh_token et profil admin_user (nom, email, rôle).

Étape D — Tableau de bord

Redirection vers /admin (Vue d’ensemble). Toutes les requêtes API portent le Bearer token ; 401 → retour login.

Déconnexion

Menu utilisateur (coin droit) → POST /api/admin/auth/logout → purge localStorage → /admin/login.

Rôles : ADMIN, MANAGER, SUPPORT (schéma base). L’interface actuelle partage les mêmes écrans pour tous les rôles connectés ; affiner les droits par rôle reste une évolution possible.

Vue d’ensemble — tableau de bord admin

Page d’accueil après connexion. Grille bento personnalisable par les administrateurs (« Personnaliser »).

  1. Indicateurs temps réel. Données chargées via AdminDataProvider : utilisateurs, transactions, KYC, APE, codes parrain, leads PEE.
  2. Cartes par défaut. AUM (dépôts + investissements + courbe), clients, activité récente, CTA KYC, mini-stats transactions.
  3. Mode édition. Ajouter / modifier / masquer / réordonner des cartes ; largeur (1–12 colonnes) et hauteur (1–4 rangs). Modèles rapides (KYC, APE, PEE, AUM).
  4. Sources de données. Métriques trésorerie, transactions, KYC, APE, PEE, parrainage ; listes (transactions, file KYC, APE récentes, leads PEE) ; liens CTA vers les sections détaillées.
  5. Persistance. Configuration en base (dashboard_cards), API /api/admin/dashboard-config.

Opérations — flux métier admin

Transactions (/admin/transactions)

  1. Liste des intentions de transaction (dépôt, investissement, retrait) avec filtres et recherche.
  2. Ouverture du tiroir détail : client, montant, référence, statut, dates.
  3. Si statut PENDING : l’admin peut approuver (→ COMPLETED) ou rejeter (→ FAILED), avec note optionnelle.
  4. Synchronisation Didit : les dépôts post-KYC peuvent aussi être mis à jour automatiquement via webhooks ; la file admin couvre les cas manuels.

APE Sénégal (/admin/ape)

  1. Consultation des souscriptions (identité, montant CFA, code parrainage, référence).
  2. Statuts : PENDING → PAYMENT_INITIATED → PAYMENT_SUCCESS / PAYMENT_FAILED / CANCELLED.
  3. Changement de statut manuel depuis le tiroir détail (suivi opérationnel si écart avec InTouch).

Réconciliation Intouch (/admin/reconciliation)

  1. Import d’un export transactions Intouch (fichier).
  2. Rapprochement automatique avec les souscriptions APE (correspondance exacte, écart de montant, non trouvé).
  3. Synthèse : matches, écarts, lignes orphelines côté Intouch ou côté APE.

Acquisition & conformité

Codes parrainage & PEE

  1. Codes parrainage — création et gestion des codes pour campagnes APE (usage, expiration, activation).
  2. PEE Leads — suivi des prospects Plan Épargne Entreprise issus des formulaires marketing.
  3. Leads abandonnés — brouillons d’onboarding (email/téléphone partiels, étape atteinte, score) ; statuts : abandonné, contacté, converti, ignoré ; notes admin.

Utilisateurs & KYC

  1. Utilisateurs — recherche client, consultation profil, modification du statut KYC global (PENDING, UNDER_REVIEW, APPROVED, REJECTED), liste des documents.
  2. Vérification KYC — file centrée sur les documents (pièce, selfie Didit) ; visualisation, notes, Approuver / Rejeter par document.
  3. Complément Didit. Le parcours client T5 alimente ces documents ; le webhook Didit peut aussi faire évoluer le statut utilisateur sans action admin.
